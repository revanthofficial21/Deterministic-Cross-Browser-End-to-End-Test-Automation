Portfolio case study

Making browser tests trustworthy again — by measuring the flakiness instead of arguing about it

A two-semester capstone that turned "our end-to-end tests are flaky" into a number, then moved the number: 50.0% of test cases flaky before, 0.0% after.

Mr. RK · solo build, supervisor-reviewed Node · Playwright · Selenium · AWS 8 months · CP1 + CP2

The problem

Browser end-to-end tests are the only automated tests that see the product the way a user does, and the ones teams switch off first. Asynchronous rendering, variable network timing and shared login state make them fail without a code change. Industry reports 16% of Google's test targets showing some flakiness and at least 2.5% of developer time spent managing it — but the cost that matters is trust: a red build that might be lying gets ignored.

Most treatments are advice ("use auto-waiting"). I wanted to know how much each layer of the test-execution system is worth, measured under one frozen envelope.

What I built

  • An instrumented application under test with the failure modes built in: deferred rendering, a hydration window where controls look enabled before listeners attach, cookie auth, per-user state, and a control surface for latency, errors and partial failure.
  • Two harnesses over one workload — a fixed-sleep baseline and an auto-waiting candidate — plus a one-switch isolation layer, so the comparison isolates one variable at a time instead of comparing two frameworks.
  • A campaign runner and analysis producing flakiness rates with Wilson intervals, run-level rates and A→B→C contrasts from per-test JSONL.
  • Five negative tests (intermittent failure, shared auth, stripped evidence, telemetry gap, partial failure) and a recovery campaign that scores an injection as recovered only if state matches and nothing is duplicated or lost.
  • A diagnosis rubric with five observable criteria and named anchors, plus tooling that scores real trace bundles and refuses to name a cause it cannot support.
  • An AWS testbed in Terraform: Fargate tasks pinned to a frozen envelope, S3 for bundles, FIS for platform-level faults.

Two things that went wrong

Both are the part I would actually talk about in an interview.

My scorer had the bug it was built to catch. With a bundle containing no evidence at all it returned "telemetry gap" rather than "insufficient evidence", because it compared the count of missing signals against the count of criteria. NT-3 failed, the rule changed to treat a zero as a refusal, and the test passed. An instrument that cannot tell "no evidence" from "partial evidence" would have inflated the score it produces.
The rubric then found a defect in my own evidence path. Five failing bundles scored 76/100 — below threshold — and the cause was not the scorer: four bundles contained only the runner's own trace, because Playwright flushes the browser trace when the context closes and loses it on an early failure. Recording explicitly in a test-scoped fixture fixed it: every bundle produced afterwards scores 100/100.

Cost of determinism: the suite runs 3.4× longer, because correct synchronisation waits for state rather than guessing a duration.

What I would do next

  • Run the three-engine campaign in CI to close cross-browser consistency, which is the one KPI a single-engine container cannot answer.
  • Raise bundle coverage — currently 1 of 7 failing executions — by moving trace capture into a worker-scoped wrapper that survives a failure inside the fixture chain.
  • Replace application-level fault injection with platform-level faults (FIS against Fargate tasks) so the recovery rate is measured against faults the code cannot anticipate.

Skills this demonstrates

Test engineering: flakiness measurement, wait-strategy design, negative testing, fault injection, recovery verification. Distributed systems: isolation and state ownership, idempotency, reconciliation from a durable checkpoint. Cloud: containerised testbed design, Terraform, FIS, evidence storage with lifecycle policy. Research: pre-registered metrics, confidence intervals, and reporting a null result honestly.
