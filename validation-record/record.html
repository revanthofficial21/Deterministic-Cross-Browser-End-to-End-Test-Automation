1. The limitation claimed by the project

End-to-end browser tests fail intermittently because of asynchronous rendering, variable network timing and shared authentication state, until the team stops trusting them. The charter requires this limitation to be reproduced with versioned evidence, or validated by a named stakeholder, before implementation proceeds.

2. Reproduction evidence

The limitation was reproduced against an instrumented application under test with asynchronous rendering, a hydration window, cookie authentication and per-user server-side state. A fixed-sleep test suite was executed repeatedly under a frozen resource envelope.

EnvironmentChromium 158.0.8127.18 · Playwright 1.49.0 · Node 20.20.2 · 2 vCPU container · 4 parallel workers
Workload8 end-to-end test cases: sign-in, order list, total reconciliation, order creation, settings persistence, filtering, post-action consistency, multi-item flow
Envelope80 ms base latency + U(0, 240) ms per API call · 100 ms deferred render · 800 ms fixed wait · identical versions for all conditions
Repetitions8 suite executions, each starting from freshly seeded state
Observed result50.0% of test cases were flaky (4 of 8 both passed and failed, Wilson 95% CI 21.5–78.5%) · 100% of suite executions contained at least one failure · 42.2% of individual test executions failed
Commandnode scripts/campaign.mjs --condition A --reps 8 --workers 4 then node scripts/analyze.mjs results
Artefactsresults/A.jsonl (per-test records), results/manifest.jsonl (envelope per repetition), results/summary.md (rates and intervals), results/figures/
Same system, synchronisedWith state-based auto-waiting and per-worker isolation: 0 failures in 112 test executions across 14 repetitions, so the effect is attributable to the execution system rather than to the application

3. What this evidence establishes, and what it does not

  • Establishes: under this workload and envelope, a fixed-sleep, shared-account suite is intermittently unreliable at a rate that would cause a team to distrust it, and the unreliability is removable by the execution system rather than by rewriting the application.
  • Does not establish: that every web application fails at this rate, or that the rate generalises beyond this workload, envelope and engine.
  • Not covered here: cross-browser consistency (needs three engines), the platform-level fault campaign, and the diagnosis score (needs two independent raters).
